## Findings

### A4-F01 — P1 — Direct Supabase writes bypass @ega/application workflow authority

**Reviewer:** A4 application architecture
**Area:** `apps/web/src/lib/mcp/write-tool-handlers.ts:19-237`

**Finding:** Write handlers insert directly via `client.from("projects").insert(...)` rather than `createProject(actor, repo, input)` etc. This bypasses validation, slug normalization, scope checks, and duplicates workflow rules. Transport should be thin; durable rules belong in `@ega/application`.

**Evidence:**
- `write-tool-handlers.ts:43` `projects` insert with manual slug logic vs `packages/application/src/projects/service.ts:28` `normalizeProjectSlug` + `repository.createProject`
- `write-tool-handlers.ts:78` tasks insert without `repository.getScope` check for project/goal ownership
- `ARCHITECTURE.md:146` intended flow `→ @ega/application → @ega/data-access → RLS` — current skips application

**Risk:** Forked validation, missed invariants (e.g., goal must belong to project, blocked reason required), harder to keep web/mobile/server consistent.

**Required fix:** Delegate to `@ega/application` services via `Supabase*Repository` adapters; keep Supabase client request-scoped but route through ports. Add regression test that wrong project/goal is rejected.

**Assigned fix task:** `FIX1-T1`

### A5-F02 — P1 — Idempotency ledger not wired into write handlers

**Reviewer:** A5 MRTR/retry/idempotency
**Area:** `apps/web/src/lib/mcp/write-tool-handlers.ts`, `drizzle/0047_mcp_mutation_receipts.sql`

**Finding:** Ledger table and `mcp_claim_mutation_receipt` / `mcp_store_mutation_result` exist but handlers never call them. `operationId` is parsed but not used to guard against retries/concurrent duplicates. Spec requires: same operationId+same args → replay cached result; different args → 409; concurrent → one effect.

**Evidence:**
- `write-tool-handlers.ts:50` `createTask` checks `operationId` presence but no `mcp_claim_mutation_receipt` call
- `request-state.ts` codec exists but not used for `operationId` binding
- `drizzle/0047...` functions defined but no handler invokes them

**Risk:** Client retries (network, audit failure) can create duplicate projects/tasks/timers; concurrent timer starts could violate `task_sessions_owner_open_unique` but ledger not providing replay.

**Required fix:** Before mutation, `SELECT mcp_claim_mutation_receipt(tool, opId, argsHash)`; if `is_replay` return cached; if `is_conflict` return 409; after mutation `mcp_store_mutation_result`. Add concurrent duplicate test.

**Assigned fix task:** `FIX1-T2`

### A1-F03 — P2 — `server/discover` and modern header validation not yet via `createMcpHandler`

**Reviewer:** A1 MCP protocol/SDK
**Area:** `apps/web/src/lib/mcp/web-transport-handler.ts`, `route-runtime.ts`

**Finding:** Handler still uses `WebStandardStreamableHTTPServerTransport` (v1 stateless) not `createMcpHandler(factory, {legacy:'stateless'})`. Modern `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` are not explicitly validated (transport may, but not proven), and `server/discover` is not served with `ttlMs:0, cacheScope:'private'`.

**Evidence:**
- `web-transport-handler.ts:42` `new RuntimeMcpServer` + `WebStandardStreamableHTTPServerTransport` — no `createMcpHandler`
- `support-2026-07-28.md` § Serving the 2026-07-28 revision — `createMcpHandler` is the entry
- No `getDiscoverResult` handling observed

**Risk:** Not fully 2026-07-28 conformant; modern discovery/caching may be missing.

**Required fix:** Migrate to `createMcpHandler(() => server, {legacy:'stateless'})` per spec or prove equivalence with test using `@modelcontextprotocol/client` `StreamableHTTPClientTransport` against `handler.fetch`. Add test that `server/discover` returns private cache hints.

**Assigned fix task:** `FIX1-T3`

### A2-F04 — P2 — Permission-aware `tools/list` still advertises writes when globally disabled or without workspace_manager

**Reviewer:** A2 OAuth/authorization
**Area:** `apps/web/src/lib/mcp/server.ts`, `route-runtime.ts`

**Finding:** `registerMcpTools` registers all write tools whenever `writeHandlers` provided; `route-runtime` creates `writeHandlers` whenever `MCP_WRITES_ENABLED=true` globally, but does not filter per-principal permissions. A `read_only` grant still sees `ega_create_project` in `tools/list`, then gets `PERMISSION_DENIED` at call time. Spec requires permission-aware discovery: unauthorized writes should not be advertised.

**Evidence:**
- `route-runtime.ts:84` `createWriteHandlers(config)` — only checks global `writesEnabled`, not `principal.permissions`
- `server.ts: registerMcpWriteTools` — no per-request filtering
- Prompt §5: "Unauthorized write tools should not be advertised."

**Risk:** Information leakage, poor UX, and extra attack surface (clients may probe).

**Required fix:** Make `createMcpHandler` factory per-request aware of `principal` (load grant before server creation) and `registerMcpTools` conditionally on `hasMcpPermission(principal.permissions, 'projects.create')` etc., or implement `tools/list` handler that filters. Add test: read_only `tools/list` excludes writes; workspace_manager includes them; `MCP_WRITES_ENABLED=false` hides all writes.

**Assigned fix task:** `FIX1-T4`

### A3-F05 — P2 — MRTR `requestState` not yet bound to grant/version/resource/target and not revalidated between rounds

**Reviewer:** A3 database/security, A5 MRTR
**Area:** `apps/web/src/lib/mcp/request-state.ts`, `write-tool-handlers.ts`

**Finding:** Codec exists and is HMAC-verified with TTL, but binding is generic `T extends Record<string, unknown>` — callers not yet enforce that `p` contains `{user, client, grantId, grantVersion, resource, tool, operationId, argsHash, target, phase}` and that second-round revalidates grant/status/version, ownership, target state. `clearCompletedToday` (the one required MRTR) has no handler yet.

**Evidence:**
- `request-state.ts:30` `canonicalJson(value)` — no mandatory field check
- No `clearCompletedToday` handler with `input_required` return
- No test for grant revoked between rounds, args tampered, target changed

**Risk:** Stale authorization (grant revoked mid-flow) could still mutate; tampered args could change target project.

**Required fix:** Define `McpRequestState = {user, client, grantId, grantVersion, resource, tool, operationId, argsHash, targetId?, phase, exp}`; `mint` asserts; `verify` returns typed; handlers on re-entry `loadActiveMcpGrant` and compare `permissionsVersion`/`status`, reload target row and compare `updated_at` or `owner_user_id`. Implement `ega_clear_completed_today` with `inputRequired` and cross-instance continuation test (mint on instance A, verify on instance B).

**Assigned fix task:** `FIX1-T5`

### A7-F07 — P3 — `operationId` missing from some write schemas makes idempotency optional

**Reviewer:** A7 adversarial
**Area:** `apps/web/src/lib/mcp/server.ts:202-259`

**Finding:** `createProject`, `updateProjectStatus`, `createGoal`, `updateTask`, `planTaskForToday` have `operationId` optional, while `createTask`, `startTimer`, `stopTimer` require it. Prompt says every non-idempotent mutation needs durable `operationId`. Optional allows callers to skip, losing exactly-once.

**Evidence:** `server.ts:206` `operationId: z.string().uuid().optional()` for 5 tools

**Risk:** Clients omitting `operationId` can create duplicates on retry.

**Required fix:** Make `operationId` required for all mutating tools (5 optional → required) or document as advisory and generate server-side idempotency key per request (less ideal). Prefer required.

**Assigned fix task:** `FIX1-T7`
